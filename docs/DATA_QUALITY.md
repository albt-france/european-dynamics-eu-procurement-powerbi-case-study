# Data quality: what was found in TED and FTS, and how it was handled

Every rule below is implemented in code (file in brackets) and, where it can be counted, checked in
`sql/06_quality_checks.sql` (results in `data/processed/qa_checks.csv` and on the report's hidden documentation page).
Tone: these are properties of open administrative data, not judgements on buyers or suppliers.

| # | Issue found | Handling | Where |
|---|---|---|---|
| DQ-01 | **TED changed format in 2023.** Legacy notices (to Oct 2023) are in the yearly CSV subset, one row per award; eForms notices (from Nov 2023) are only in the API / XML, where search fields are notice-level arrays that do not say which lot each winner took. | Two pipelines: legacy CSV rows as published; European Dynamics eForms notices parsed **lot by lot from the XML** (lot result -> winning tender -> tendering party -> organisations). The eForms market context uses search fields at **notice level** (`LotId = '(notice)'`), number of offers kept only for single-lot notices. Procedure and buyer-type codes of both formats mapped to one list. | `build_dataset.py`, `ref.Procedure`, `ref.BuyerType` |
| DQ-02 | **Name variants.** 68 distinct spellings of European Dynamics entities: case, punctuation, legal-form spellings ("S.A.", "SA"), long legal names, Greek script ("ΕΥΡΩΠΑΪΚΗ ΔΥΝΑΜΙΚΗ"), typos ("Dyamics", "Deutschlang"), consortium labels, FTS aliases after a `*`. | Normalised name (upper case, punctuation removed) matched against **17 LIKE patterns** with priorities in `ref.EntityAlias` (8 entities + "not ED"). Audit table `dwh.EntityNameMap`. Same result reproduced with a **fuzzy merge in Power Query** for FTS (threshold 0.8). | `02_reference_data.sql`, `04_etl_load_dwh.sql`, `FtsStaging.pq` |
| DQ-03 | **Winner reference pointing to the buyer's service provider.** In eForms notices of Irish (53) and Lithuanian (10) buyers, the tendering party of the winning tender is named as another company, but its organisation reference points to the European Dynamics entity that the same notice lists as the buyer's *service provider*. The TED search index therefore lists European Dynamics as winner of, for example, water works or vehicle hire. | Excluded (63 lot rows). Rule: all ED organisations in the winning party are service providers of the buyer, and the tendering party name is another company. | `build_dataset.py` (`dq_excluded`) |
| DQ-04 | Same pattern **without** a tendering-party name, on non-IT contracts (Ireland 5, Lithuania 2). | Excluded (7 rows). IT contracts with the same pattern are kept (1 row), as the award is plausible. | idem, QA10 |
| DQ-05 | **Multi-winner framework agreements and consortia.** A lot of a framework can have 5-8 winning tenders, each published with the full framework value (a ceiling, not spending). | `ValueSplitEUR` = lot value / winning tenders in the lot (sums back to the lot value). `CountedValueEUR` keeps the full value once per lot for transparency. Consortium values are not split further (one tender). Counts lead the analysis. | `04_etl_load_dwh.sql` step 3, QA07 |
| DQ-06 | **Joint procurement**: legacy buyer names concatenated ("Agency A---Agency B---..."). | Lead (first) buyer kept, flag `joint_procurement` in staging. | `build_dataset.py` |
| DQ-07 | **Non-Latin buyer names** (Greek, Bulgarian) became empty after a first ASCII-only normalisation and fell into one "unknown" buyer (2,253 rows, check QA06 = WARN). | Normaliser fixed to keep letters of every script; QA06 now 0. | `build_dataset.py::buyer_key` |
| DQ-08 | **Exact duplicate award rows** in the legacy CSV (same notice, lot, award and winner). | Removed (61 rows). | step 3a, QA02 |
| DQ-09 | **Implausible values** (above EUR 2 bn or below EUR 1, e.g. placeholders). | Value set to NULL, row kept as an award (325 rows, 4 of them European Dynamics). | step 3b, QA08 |
| DQ-10 | **Missing values**: number of offers missing on 1,280 of 6,038 rows; no value at all on 9% of European Dynamics awards. | Kept as BLANK; averages and shares use only rows where the field is stated (denominators say so). | measures, QA09 |
| DQ-11 | **Currencies**: a few eForms values in GBP, PLN, USD, MKD. | Converted with the ECB annual average of the publication year; a currency without an ECB reference rate (MKD, 4 rows) gets a NULL value instead of being counted as euros. Legacy values were already converted to EUR by the Publications Office. | step 2 |
| DQ-12 | **FTS amounts are commitments**, not payments; one row per budget line; "X - " prefix marks former departments; some beneficiaries are consortia (name lists partners). | `ContractedEUR` (beneficiary's share) summed; the commitment total (all beneficiaries) is never summed; prefix removed; consortium flagged and attributed to the lead entity. Reconciled to the euro (QA03). | `FtsStaging.pq`, `04_etl_load_dwh.sql`, QA03 |
| DQ-13 | **Buyer country = location of the contracting authority**, so EU agencies count in their host country (Portugal for Lisbon-based agencies, Belgium / Luxembourg for most institutions). | Stated in the visuals' titles and alt text; buyer segment (EU vs national) offered as a separate axis. | report |
| DQ-14 | **2026 is a partial year** (notices published to 13 Nov 2026); FTS 2025 published mid-2026; FTS 2026 not yet available. | Labelled in YoY measures and titles; no extrapolation. | report |
| DQ-15 | **Personal data** can appear in notices (contact points, sole-trader names). | Contact, address, phone and e-mail fields are never read; eForms organisations flagged as natural persons get no name; market supplier names are kept only when they contain a company legal form, else "Other supplier (name not kept)". | `build_dataset.py`, `04_etl_load_dwh.sql` |

## Checks run on every load (summary)

16 checks: 16 PASS after the fixes above. They cover reconciliation (staging vs fact, FTS to the euro), orphan / missing
keys, double counting of lot values, outliers, unresolved entities, date continuity, procedure mapping, SIMULATED data
consistency and the RLS mapping (every agency has a user).
